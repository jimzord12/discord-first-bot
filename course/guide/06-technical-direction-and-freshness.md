# Technical direction and freshness

- **Runtime:** Bun is the actual application runtime, package manager, and test runner. Do not silently switch execution to Node.js or another JavaScript runtime. Distinguish installing with Bun from executing with Bun. discord.js documents Node.js as its supported runtime and lists Bun only as an installer, so verify early that connecting, reconnecting, and shutdown work on Bun. If a runtime-specific problem appears, diagnose it and discuss options rather than switching runtimes.
- **Type safety:** Use strict TypeScript, ES modules, and discord.js. Enable `strict` and `noUncheckedIndexedAccess`, explaining relevant diagnostics rather than suppressing them reflexively.
- **Type checking:** Establish a `typecheck` script in Session 02 and use it throughout the course. Running TypeScript is not type checking: Bun strips types without checking them. Choose and document one checker at setup: `tsc --noEmit`, or `bun check` if the installed Bun provides it. With `bun check`, pin the `typescript` dev dependency to the version Bun's checker reports so the editor and checker agree, and keep the script named `typecheck` (a `check` script would shadow `bun check`). Recent TypeScript majors changed `tsconfig` defaults, so start from Bun's current recommended configuration rather than older tutorials, and set the editor to use the workspace TypeScript version.
- **Initial versions:** At setup, verify current stable, mutually compatible versions using official releases and documentation. Avoid prereleases and development-branch documentation unless explicitly justified.
- **Continuity:** Record exact versions and commit `bun.lock`. Later sessions retain the confirmed working versions. Do not reinstall everything at `latest` or silently change dependencies between chats. Recommend upgrades explicitly, explaining compatibility, migration work, and verification.
- **Reproducibility:** Use locked installs, such as `bun install --frozen-lockfile`, in CI and deployment. Keep scripts consistent across environments.
- **Dependencies:** Add packages only when needed. Skip optional native performance packages, such as `zlib-sync` and `bufferutil`, initially; introduce them only if compatibility and measured benefit justify them.
- **Documentation:** Prefer official Discord, Bun, TypeScript, discord.js, SQLite, and hosting documentation. Verify changing APIs, limits, pricing, and compatibility when relevant. If verification is unavailable, state the uncertainty rather than inventing facts. When the installed package's types, deprecation warnings, or changelog disagree with remembered APIs, trust the installed version.
- **Architecture:** Begin with one process and readable modules. Add structure when a concrete feature creates a need. Keep commands, persistence, and background work understandable without building a generic framework.
