# Course outline

Each session is a separate chat in the same ChatGPT Project. Sessions span multiple exchanges; never dump a full session into one response. Aim for 60–90 minutes of active work, allowing extra time for manual typing, exercises, and setup. Split a session into smaller sittings when useful.

| Session / chat title | Content | Completion checkpoint |
| --- | --- | --- |
| [01 — Discord architecture and bot fundamentals](../01-discord-architecture-and-bot-fundamentals.md) | Application versus bot user; guilds, users/members, channels, roles, and IDs; REST versus Gateway; interactions versus webhooks; permissions versus intents; what Discord hosts and what we host. | I can trace how a user action reaches the bot and how its reply returns. |
| [02 — Developer Portal and project setup](../02-developer-portal-and-project-setup.md) | Private test server; application and bot setup; installation scopes and minimal permissions; Bun setup; strict TypeScript; type-check script; environment validation; secrets; Git and project scripts. | A reproducible project validates its configuration, passes type checking, and connects to Discord. |
| [03 — Minimum working bot and local development](../03-minimum-working-bot-and-local-development.md) | Guild-scoped `/ping` registration and handling; registration versus execution; local startup and restart workflow; diagnose token, scope, permission, and command-registration failures. | `/ping` works in my test server while the bot runs on my computer. |
| [04 — Modular commands and typed options](../04-modular-commands-and-typed-options.md) | Command module contract, a simple registry/router, typed options and subcommands, input validation, and separating command logic from Discord handling. | Multiple commands run through a clear, typed router. |
| [05 — Interaction lifecycle and error handling](../05-interaction-lifecycle-and-error-handling.md) | Acknowledgment deadlines, deferral, follow-ups, private responses, messages/embeds, safe async error handling, and useful logging. | Slow and failing commands produce understandable feedback without unhandled failures. |
| [06 — Interactive Discord components](../06-interactive-discord-components.md) | Buttons and structured component identifiers; select menus and modals briefly, building only the one the poll actually uses; global routing versus temporary collectors, authorization, and mention safety. | An in-memory poll supports voting and live counts, with voting and management rules enforced. |
| [07 — SQLite persistence and server configuration](../07-sqlite-persistence-and-server-configuration.md) | SQL context; `bun:sqlite`; foreign keys; WAL; numbered migrations; prepared statements; constraints; transactions; guild-scoped settings; persistent component state. Plan two sittings: schema, migrations, and query tests; then wiring polls and settings plus restart checks. | Polls, votes, and settings survive restarts; duplicate votes are prevented by database constraints; existing poll buttons still work. |
| [08 — Gateway events, intents, and cache boundaries](../08-gateway-events-intents-and-cache-boundaries.md) | Select an event such as member joins; minimal required intents and any privileged-intent setup; cache/partial entity limitations; permissions before sending; configurable behavior. | A configured event response works in the test guild with the required intents and permissions understood. |
| [09 — Persistent reminders, time zones, and recovery](../09-persistent-reminders-time-zones-and-recovery.md) | `/remind`; unambiguous time input; UTC instants and time-zone conversion; persisted due times; a polling scheduler; missed work after downtime; delivery failures and duplicate-delivery tradeoffs. | Reminders survive restarts, and overdue or failed deliveries follow an explicit, tested policy. |
| [10 — Testing, reliability, and CI](../10-testing-reliability-and-ci.md) | Consolidate earlier tests; unit and database integration tests; file-backed restart/migration checks; rate-limit awareness; reconnect behavior; graceful shutdown; GitHub Actions type-check and test jobs. | Meaningful checks pass locally and in CI; startup, shutdown, and restart behavior are verified. |
| [11 — Free Linux hosting and deployment](../11-free-linux-hosting-and-deployment.md) | Recheck free-host eligibility; provision Linux VM; SSH access and basic hardening; Bun; locked dependencies; secrets; `systemd`; logs; persistent database path; backups and restore; updates and rollback. | The bot runs independently of my computer, restarts after crashes/reboots, and has a verified backup/restore procedure. |
| [12 — Capstone and independent extension](../12-capstone-and-independent-extension.md) | Implement one feature from a written requirement; verify two-server isolation; appropriate global registration; security and operations review; brief scaling/sharding context. | A deployed bot I understand end-to-end and can extend independently. |
| [13 — WebSocket fundamentals and Discord Gateway deep dive](../13-websocket-fundamentals-and-discord-gateway-deep-dive.md) | HTTP request/response versus persistent bidirectional WebSocket communication; opening, sending, receiving, errors, and closing; a small local Bun echo server/client typed by the learner; transport-level ping/pong versus Discord application-level heartbeats; Gateway authentication, intents, event envelopes, sequence numbers, reconnect/resume, and what discord.js handles. Keep the echo exercise separate from the bot; continue using discord.js for the bot connection. | I can build and explain a local WebSocket exchange, observe disconnect behavior, and trace the Discord Gateway lifecycle while distinguishing SDK responsibilities from application responsibilities. |

Session 13 is a dedicated workshop added at the learner's request. Its full tutorial can be taken earlier, after Session 03, if it would help understanding; retain the existing session numbers. Give the introductory explanation before Session 02's first connection regardless.

Keep `/ping` deliberately small in Session 03, then extract structure in Session 04 so the motivation is visible. Introduce basic error handling whenever needed; Session 05 deepens it rather than postponing all safe handling.
